# Murdle-like 逻辑推理网页游戏 · 设计方案与开发计划

> 版本：v0.1（设计稿）
> 日期：2026-09-16
> 状态：待评审

---

## 1. 项目概述

### 1.1 游戏定位

一款类似 **Murdle**（G. T. Karber 创作的每日逻辑网格推理游戏）的网页推理游戏：
玩家在多名嫌疑人、多种作案工具、多个案发现场之间，根据若干条线索，
通过排除法在逻辑网格中打 ✓ / ✗，最终推理出「**谁 — 用什么 — 在哪里**」的唯一答案。

- 类型：单人 · 逻辑推理 · 逻辑网格（Logic Grid / Zebra Puzzle）
- 平台：网页（桌面 + 移动浏览器响应式）
- 节奏：每日一题（Daily）+ 关卡模式（Campaign）双轨

### 1.2 核心体验目标

1. **推理性**：所有题目保证唯一解，且解必须能通过纯逻辑推导得到（不靠猜）。
2. **易上手**：交互极简 —— 点格子循环切换 ✓ / ✗ / 空白。
3. **有节奏**：每题 3–8 分钟；自动笔记降低门槛，高手模式可关闭。
4. **可复玩**：程序化生成无限关卡 + 每日谜题（种子确定性生成，人人同题）。

## 2. 核心玩法设计

### 2.1 谜题结构

每道题包含三个类别（Category），每类 N 个选项（N 依难度为 4 / 5 / 6）：

| 类别 | 示例 |
|------|------|
| 嫌疑人 Suspects | 教授、管家、歌手、画家…… |
| 凶器 Weapons | 烛台、毒药、匕首、绳索…… |
| 地点 Locations | 书房、温室、餐厅、画廊…… |

**目标**：为三个类别各确定一个选项，使三者一一对应（每个选项在题中恰好出现一次），
即找出 (嫌疑人, 凶器, 地点) 的三元组绑定关系。

### 2.2 玩家操作

- 在 N×N 逻辑网格（嫌疑人×凶器、嫌疑人×地点、凶器×地点 三个子网格）中标记：
  - **左键 / 点按**：循环 `空 → ✓ → ✗ → 空`
  - **右键 / 长按**：直接打 ✗（快速排除）
- 标记 ✓ 时**自动推论**：同一行/列其余格子自动打 ✗（可在设置中关闭）。
- 标记与某 ✓ 同行同列的另一个 ✓ 冲突时，红色高亮提示矛盾。

### 2.3 流程

```
选关 / 每日题
   │
   ▼
开场小剧情（1–2 句，营造氛围，可选）
   │
   ▼
阅读线索列表 ──► 在网格中推理标记 ──►（可随时重看线索）
   │
   ▼
点击「提交指控」── 选择 嫌疑人+凶器+地点 三元组
   │
   ├─ 正确：胜利结算（用时、使用提示次数、网格完成度、评分星级）
   └─ 错误：扣一颗心（共 3 颗），错误选项在网格中自动标灰并给出文本提示
```

### 2.4 计分与反馈

- **星级（1–3）**由三项决定：用时、错误次数（心）、使用「提示」次数。
- **提示系统**：卡关时可点提示，系统从当前局面出发找出下一个可逻辑推导的格子并高亮；
  每用一次提示在结算中扣分。提示的实现依赖第 4 节的求解器，保证提示的每一步都是纯逻辑可达的。
- 计时器可暂停；每日题自带排行榜锚点（先本地，预留后端）。

## 3. 难度模型

| 难度 | N（每类选项数） | 线索数 | 线索复杂度 | 目标人群 |
|------|----------------|--------|------------|----------|
| 🟢 简单 | 4 | 6–8 | 只有排除类与绑定类 | 新手 |
| 🟡 中等 | 5 | 8–10 | 加入位置/相邻类 | 普通 |
| 🔴 困难 | 6 | 10–13 | 加入复合条件类 | 高手 |

难度由**生成器参数**控制（见 4.3），关卡模式按难度分章节解锁。

## 4. 谜题生成器（核心算法模块）

这是本项目的技术核心，拆成独立的 TypeScript 包 `puzzle-core/`，前后端共用。

### 4.1 生成流程

```
┌─────────────────────────────────────────────────────────┐
│ 1. 采样解：随机生成一个合法完整解                          │
│    （三个类别的双射绑定：suspect↔weapon, suspect↔location）│
│                                                         │
│ 2. 生成候选线索池：从解出发，枚举所有「在该解下为真」的    │
│    原子线索（见 4.2），每条线索标注其「逻辑信息量」        │
│                                                         │
│ 3. 贪心选线索：从池中按难度配额挑选线索子集 S             │
│    - 约束：S 必须唯一确定该解（用 4.4 求解器验证）        │
│    - 目标：在满足唯一解的前提下，让线索总数与难度档位匹配， │
│      并尽量让中间推理步数落在目标区间                      │
│                                                         │
│ 4. 验证：                                                │
│    a) 唯一解检查 —— SAT/回溯计数，解数量必须 == 1          │
│    b) 可解性检查 —— 用「类人推理求解器」从空网格出发，      │
│       不用试错回溯也能推出答案（保证不需要猜）             │
│    c) 失败则回到步骤 2/3 重新选                           │
│                                                         │
│ 5. 输出：PuzzleBundle { 主题, 解, 线索[], 难度, seed }     │
└─────────────────────────────────────────────────────────┘
```

### 4.2 线索类型库（原子线索）

每种线索都是「在完整解的语义下可判定真假」的谓词。按信息量从低到高：

| 类型 | 模板示例 | 逻辑形式 |
|------|----------|----------|
| L1 直接排除 | 「教授没有用过匕首。」 | weapon(教授) ≠ 匕首 |
| L2 直接绑定 | 「管家用的是毒药。」 | weapon(管家) = 毒药 |
| L3 互斥绑定 | 「歌手和用绳索的人不是同一人。」 | suspect(绳索) ≠ 歌手 |
| L4 共同出现 | 「教授案发时和用烛台的人一起在温室。」 | 三者两两绑定（教授+烛台+温室 同案） |
| L5 条件否定 | 「如果有人在画廊，那绝不是歌手。」 | location(x)=画廊 ⇒ x ≠ 歌手 |
| L6 位置关系 | 地点排成一列时：「画廊在书房左边第二间。」 | 地点线性序约束（仅当地点有地图/序列语义时启用） |
| L7 否定组合 | 「匕首既不在温室，也不在画廊。」 | location(匕首) ∉ {温室, 画廊} |

> 设计原则：**每条线索在渲染层可模板化成一句自然语言**，且带主题词表（侦探、宫廷、太空、校园……主题决定名词库与文案语气）。

### 4.3 难度控制参数

```ts
interface GeneratorConfig {
  n: 4 | 5 | 6;              // 每类选项数
  clueCount: [min, max];     // 线索数量区间
  typeQuota: Partial<Record<ClueType, [min, max]>>; // 各线索类型的数量配额
  requireNoGuessing: boolean; // 必须纯逻辑可解（默认 true）
  requireNoSubgrid: boolean; // 困难模式：禁用“单看一个子网格就能解”的题
  rngSeed: string;           // 确定性随机种子（每日题 = 日期字符串）
}
```

### 4.4 求解器（solver）

- **模型**：三类双射约束 + 线索谓词约束，本质是一个有限 CSP。
- **实现**：位运算回溯（每格 1 bit，N≤6 时状态极小）+ 解计数。
  - `countSolutions(puzzle, limit=2)`：>1 即不唯一，快速剪枝。
- **类人推理求解器（hint engine）**：只使用「匹配格子 → 行列排除」「唯一候选」等
  人类可理解的推理规则逐级推进，每步规则可命名、可解释 —— 这正是**提示系统**和
  「保证不用猜」验证的来源。

### 4.5 每日谜题

`seed = "murdle-like:2026-09-16"`，用带种子的 PRNG（如 `seedrandom` / `mulberry32`）
驱动生成器，保证同一天所有玩家得到同一道题；主题按周轮换。

## 5. 前端架构（React）

### 5.1 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 构建 | Vite 6 + TypeScript (strict) | 快速 HMR，类型安全 |
| UI 框架 | React 19 + Tailwind CSS 4 | 网格类 UI 用工具类最快 |
| 状态管理 | Zustand | 谜题/网格状态频繁细粒度更新，比 Context 性能好 |
| 路由 | React Router | 关卡选择 / 游戏 / 结算 / 每日题 |

### 5.3 前端状态模型

```ts
// Zustand gameStore
interface GameState {
  puzzle: Puzzle;                     // 当前题（含线索）
  marks: Record<CellKey, Mark>;       // 玩家标记: 'yes' | 'no' | undefined
  contradictions: CellKey[];          // 冲突高亮
  hearts: number;                     // 3 → 0
  hintsUsed: number;
  elapsedMs: number;
  phase: 'reading' | 'solving' | 'accusing' | 'won' | 'lost';
  applyMark(cell, mark): void;        // 含自动推论（可关）
  accuse(triple): 'correct' | 'wrong';
  requestHint(): Hint;                // 调 humanSolver
}
```

### 5.4 关键交互设计

- **网格**：三个 N×N 子网格（嫌疑人×凶器 / 嫌疑人×地点 / 凶器×地点）纵向排布或 Tab 切换（移动端）。
  每格是按钮，支持键盘操作（方向键移动、空格循环标记、X 键打 ✗）——网页游戏无障碍友好。
- **自动推论**：打 ✓ 后同行列自动 ✗，以半透明标记显示（区别于手动 ✗），撤销时联动回滚。
- **线索笔记**：每条线索可手动划线（排除已用线索）。
- **矛盾提示**：不直接告诉玩家错在哪，只高亮冲突格，保护推理乐趣。
- **移动端**：格子 ≥ 44px 触控目标；✓/✗ 用点按循环，长按直达 ✗。

## 6. 美术与氛围方向

- **视觉基调**：手绘侦探笔记本风 —— 米白纸感背景、深色墨线、✓/✗ 用钢笔笔触；
  避免科技感渐变与卡片套卡片。
- **主题皮肤**：谜题主题（侦探庄园 / 宫廷晚宴 / 太空站 / 校园祭）决定名词库与配色点缀。
- **动效**：克制 —— 标记落笔小动画、扣心抖动、结算盖章效果；无滚动触发动效。
- 具体视觉方向在动工前用设计检索工具收集参照后再定稿（避免默认 AI 审美）。

## 7. 开发计划（里程碑）

> 假设单人全职当量，总计约 **4 周**。如需更快，M4/M5 可裁剪。

| 里程碑 | 内容 | 验收标准 | 周期 |
|--------|------|----------|------|
| **M1：核心引擎** | `puzzle-core`：类型、RNG、线索谓词、回溯 solver、解计数 | 1,000 道随机生成题 100% 唯一解；单元测试覆盖 | 第 1 周 |
| **M2：生成器 + 类人求解器** | 贪心选线索、难度参数、humanSolver（命名推理规则）、fast-check 属性测试（「唯一解 ∧ 无猜测可解」）、每日种子 | 三档难度各抽测 200 题全部通过属性测试；每题可产出推理步骤序列 | 第 2 周 |
| **M3：前端可玩闭环** | Vite+React 工程、网格交互、线索列表、自动推论、提交指控、心/提示/计时、localStorage 进度 | 桌面 + 移动浏览器可完整玩通一道题；键盘可操作 | 第 3 周 |
| **M4：内容与设计** | 4 套主题词库（雾岭庄园/环轨空间站/宫廷晚宴/校园祭，各含四类词表）、关卡章节（含特别篇「雾中时序」K=4）、结算评分星级、视觉风格定稿与打磨、动效 | 视觉走查通过；每主题实跑生成验证。原计划的「预生成 ≥50 关入库」改为**按需生成**（引擎实测 p50 ≤ 331ms，无需题库入库） | 第 4 周 |
| **M5：发布加固** | 每日题模式 + 分享卡片（生成结果图/文本）、PWA（离线可玩）、性能与无障碍检查、部署（GitHub Pages / Vercel） | Lighthouse ≥ 90；PWA 离线可玩；CI 跑核心测试 | 第 4 周末 |

### 风险与对策

| 风险 | 对策 |
|------|------|
| 生成器产题率低（选线索反复不唯一） | 候选池大 + 多起点重试；单题生成预算 < 200ms 即可接受 |
| 「唯一解」但需猜（人类不可解） | humanSolver 作为硬性验收门，不通过即弃题重生成 |
| N=6 网格在手机上太小 | 移动端子网格 Tab 化，或提供「类别对选择器」折叠视图 |
| 文案模板重复感 | 每个主题准备 ≥30 条句式变体，渲染时轮换 |

## 9. 已确认决策（2026-09-16）

1. ✅ **预留四类扩展**：引擎从第一天按 K 个类别（K=3 或 4）通用设计；第四类默认为「作案时段」。枚举空间 guard：K=4 时 N ≤ 5（(5!)³ ≈ 173 万组合可承受；(6!)³ 过大改用采样启发式 + 回溯验证）。
2. ✅ **中文文案为主**（无二期英文计划，模板层预留 i18n 接口）。
3. ✅ **关卡 + 每日题两者都做，关卡先行**。
4. ✅ **一期纯本地**（localStorage），账号/排行榜留二期。
5. ⏸️ 部署目标未指定 → **默认 GitHub Pages / Vercel 静态部署**，评审时可改。

### v1 线索类型裁剪说明

M1/M2 先实现 4 种「可直接译为网格标记」的原子线索：`EXCLUDE`（排除）、`BIND`（绑定）、
`GROUP`（≥3 类共同出现，含原版 L4）、`NOT_IN`（否定组合，即 L7）。
`IF`（L5 条件）与 `POS_REL`（L6 位置序）依赖位置/条件语义，推迟到 M2 末评估 —
加入前需先扩展 humanSolver 的规则库，否则会破坏「无猜测可解」的验收门。
